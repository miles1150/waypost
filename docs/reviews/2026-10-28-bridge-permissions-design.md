# 本地通知桥与权限编辑设计评审（2026-10-28）

范围：Waypost 本地源码、Yobiru `906ef9698224` 的收件与 Codex 桥接实现，以及本次约五台个人设备的需求。方式：独立 subagent 静态审查；本记录不证明实现测试、生产部署或真实 Codex 投递已经通过。

结论：方案可实现，保留现有消息与回执模型；权限编辑优先，桥接收缩为引用通知器。无需新 Connection 实体、服务器任务队列或通用宿主插件框架。

| 发现 | 风险 | 采纳的设计处理 |
| --- | --- | --- |
| scopes/grants 分散在多个子表 | token CAS 失败但子表仍被修改 | 同一原子批次中所有 grant 变更与审计受同一获胜操作保护 |
| token 列表缺少完整 grants 和权限版本 | 编辑界面无意清除已有授权 | 专用权限 GET 返回完整详情，PUT 使用预期版本 |
| 多个凭据可关联同一 Consumer | 改一个连接影响其他连接的进度 | 保留 Actor、Consumer、token 和全局消费者视图版本 |
| f2 使用完整权限指纹 | 增加发送权限也使读取游标失效 | 新 f3 使用读取范围指纹，独立保留旧 f2 验证路径 |
| 权限变化重新扫描 | 历史消息重复通知 | 去重身份不包含授权指纹或游标版本 |
| 空 recipient 列表有默认授权语义 | 界面误以为空列表表示不允许发送 | 保留并说明既有默认收件语义，修改时校验 default recipient |
| 本地待通知记录可能已撤权 | 失效权限仍触发旧工作 | 认证失败暂停，待发送前复核当前读取资格 |
| Codex queue 响应可能丢失 | 自动重试导致重复执行 | 发送前落盘；超时或崩溃进入 unknown，不根据历史缺失推断未投递 |
| 参考 Consumer 空页也写 ACK | 五设备空闲消耗 D1 写额度 | 通知桥不调用 ACK；游标和通知记录只写本地 |
| 引用落盘不同于完整收取 | 将通知误报为 received/processed | 业务回执由真正读取和处理的助手提交 |
| bridge 引入 native 依赖 | Cloudflare wasm 构建受影响 | 独立 Rust crate 与独立 CI/build 入口 |

## 实现评审时必须核对

- 并发 CAS、重放请求和撤销竞争不会部分更新授权；审计不能先于授权成功提交。
- 权限 GET/PUT 都使用空间所有者隔离与既有管理认证，普通助手无法自行增权。
- f3 指纹覆盖全部读取可见性依赖；f2 不被错误地按新语义接受。仅写权限变化不会破坏新游标。
- 更新完整授权时保留用户未编辑的收件人、资料和 blob 范围；不回显原始 token 或摘要。
- bridge 单实例锁覆盖恢复和发送；sending 崩溃转 unknown；回执严格匹配固定会话。
- 外部消息内容不能成为 shell、CLI、会话或本地路径配置；通知只使用可信模板和经过验证的标识。
- 30/60 秒轮询在空页不写服务器，重试和核对不产生额外心跳服务；CF 资源估算与实际测量分开报告。
- 发布记录区分本地测试、真实 D1/R2、线上 HTTP/MCP 和真实 Codex；没有实际宿主时不能宣称端到端模型执行通过。

完整方案见[设计文档](../design/0006-local-bridge-and-connection-permissions.md)。最终实现评审结果应追加实际发现和验证证据，而不是把本次设计审查直接视为代码批准。

## 首轮实现审查

审查当前工作区的权限 API、迁移、游标与 bridge 代码，尚未运行生产验收。

- 权限更新采用审计行的唯一 nonce 作为批次获胜标记，token 更新及全部 grant 子表操作均受该标记约束；未发现 CAS 失败仍改写子表的问题。f3 读取指纹与当前 feed 可见性条件一致，旧 f2 验证独立保留。
- 发现阻断上线的问题：bridge 请求固定 `limit: 100`，Cloudflare profile 最大分页为 20，实际 API 会返回 `RESOURCE_LIMIT`。已交由实现者改为使用部署允许的分页，并补测试。
- 要求所有传输都固定到 UUID，避免本机默认传输接受会话名称后可能解析到不同会话；同时给补收分页设置单轮上限，防止持续新消息让通知一直等待扫描结束。
- 补充建议：成功轮询也应有随机抖动；不可见的待发消息不要每轮无限重查；客户端使用明确的产品 User-Agent。权限详情的 editable 应反映 Actor/Consumer 停用状态，而不只检查 token。

这些发现的修复、复审结果和最终部署证据应在完成后记录；本节不构成部署批准。

## 修复后静态复审

已重新核对 bridge 实现：请求不再固定分页大小，交由服务端按部署上限选择；每轮最多补收十页；所有传输要求固定 UUID；成功轮询加入抖动；404 引用进入 blocked，权限视图重置或显式 retry-blocked 后才再查；HTTP 客户端设置产品 User-Agent。以上首轮发现已在代码中处理。

权限批次的获胜 guard、f3/f2 游标边界与 bridge 未知结果处理在本轮审查中未发现剩余阻断项。此结论只覆盖静态代码审查，仍以集成测试、实际 D1 迁移与发布验收通过为部署条件。实现者报告九项 bridge 测试通过；该报告不替代真实 Cloudflare 或 Codex 宿主验收。

## 后续发现：管理者撤权竞争

后续后端审查发现首轮静态审查漏掉的权限竞争：事务内检查了被编辑 token 的状态，但没有再次检查发起修改的空间所有者凭据或管理会话。如果管理者在请求认证后、事务执行前被撤权，仍可能成功修改助手权限。首个生产版本因此暂时回滚，修复和重新验收前不能视为完成发布。

修复将已有 `owner_authority_guard` 加到创建审计获胜标记的同一条 INSERT 条件中。没有当前管理权限就不产生获胜标记，后续 token 与 grant 更新全部不执行；事务后再次检查当前权限。该 guard 覆盖空间所有者凭据撤销、会话删除或过期及默认所有者身份停用，沿用现有 Dashboard 权限语义。需要一个在权限批次执行前撤销管理凭据的确定性回归测试，证明没有新审计行、权限版本不变且 grant 子表不变。

独立复审已核对该 guard 捕获请求的确切凭据／会话摘要，并在 cloud env 执行 `cargo test --locked --lib token_permissions`：四项通过，分别覆盖确定性并发 CAS、事务边界所有者撤销、所有者密钥替换及会话退出、旧 Principal 与 f2/f3 游标。此次复审未发现剩余阻断项；线上重新发布和 D1 验收仍由部署记录证明。

## Cloudflare 静态资源验收路径

`scripts/prepare_dashboard_assets.py` 将 app、i18n、memory、样式和 locale 文件生成内容指纹路径，并改写部署 HTML。源代码及 native 测试仍使用未指纹路径。因此 Cloudflare 上 `/dashboard/app.js` 返回 404 本身不是部署失败；应先读取线上 Dashboard HTML，再请求其中实际引用的 `app.<hash>.js` 及其 locale 依赖，核对内容和安全响应头。
